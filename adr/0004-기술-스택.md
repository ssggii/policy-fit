# ADR-0004: 기술 스택

- 상태: accepted
- 날짜: 2026-07-23

## Context

Phase 5. 문서·계약이 갖춰졌고 처음으로 실행 코드의 스택을 정한다.

제약과 목표:
- **무인증·미저장·개인정보 최소수집** (PRD 9장, H4).
- **판정 로직이 순수 함수** (원자 평가기 + Kleene 조합기 + 사전분류기, ADR-0003). 규칙은 JSON 데이터, 정책 요건은 공개 정보.
- **stateless·단일 판정 엔드포인트** (`POST /verdicts`).
- **계약이 JSON Schema/openapi** (Phase 4에서 verdict·rule-dsl freeze) — 코드와 타입 공유 필요.
- **1인 개발 + AI 에이전트 루프.**
- **판정 코어가 도메인 로직 중심** — rule DSL 노드 4종·verdict 4상태·값 유형 3종·Kleene 3치의 합계형(sum type) 모델링이 핵심.
- **로드맵이 전형적 백엔드 과제를 포함** — 정책 갱신 감시(스케줄링), 정규화 배치, H3 알림 구독 영속화, 계측 집계(PRD 8장) 모두 서버·저장을 전제.
- **유지보수자 역량** — 1인 개발자가 Java엔 익숙하나 JS/TS에는 약하다. 백엔드는 능숙한 언어로 두어 판정 코어의 정확성·유지보수를 직접 책임지고, 프론트(Next.js/TS)는 AI 에이전트 주도로 작성한다.

이 전제(도메인 코어 성격, 로드맵의 백엔드 요구, 유지보수자 역량)가 바뀌면 본 결정은 재검토 대상이다.

## Decision

### D1. 아키텍처 — 별도 백엔드 서비스 + 프론트, 단일 저장소

프론트(Next.js)와 백엔드(Spring)를 **독립 서비스**로 나눈다. 단일 Git 저장소 안에 `backend/`(Spring)·`web/`(Next.js)·루트 `contracts/`(공유)를 둔다. 두 서비스는 `POST /verdicts` API 계약으로만 통신한다.

- 근거: 백엔드가 Java/Spring(D2)이므로 Next.js route handler(JS/TS)로는 구현할 수 없다. 별도 서비스는 언어 선택의 필연적 귀결이며, API 설계·레이어링·테스트·배포를 백엔드 쪽에서 온전히 다룬다.

### D2. 백엔드 — Java 21 + Spring Boot 3.x

판정 엔진(원자 평가기·Kleene 조합기·값 유형 사전분류, ADR-0003)을 Java로 직접 구현하고 `POST /verdicts`를 제공한다.

- **근거 ① 도메인 모델링 적합성:** 판정 코어는 합계형 성격이다(노드 4종·verdict 4상태·값 유형 3종). Java 21의 sealed interface + record + switch 패턴 매칭으로 표현하면 컴파일러가 **분기 누락을 강제 검출**(exhaustiveness)한다. 판정 정확도가 제품 핵심 가치(오판율 게이트, PRD 5장)라 도메인 로직의 컴파일타임 안전성이 직접 이득.
- **근거 ② 로드맵 플랫폼 적합성:** 향후 요구(갱신 감시 스케줄링·정규화 배치·구독 영속화·계측 집계)를 Spring이 1급 기능(Scheduling·Batch·Data JPA·Actuator/Micrometer)으로 제공해 조립 비용이 낮다.
- **근거 ③ 정확성·장수 지향 성숙도:** 올바름이 핵심인 장기 서비스에 JUnit·Spring Test·Bean Validation·LTS(Java 21)의 성숙한 생태계가 부합.
- **근거 ④ 선택 요인:** ①~③으로 기술적 타당성을 확인한 위에서, 기능상 대등한 후보(TS/Go) 중 이 스택을 확정한 요인은 유지보수자가 능숙한 언어라는 점이다(Java 익숙, JS/TS 취약).
- **프라이버시 제약(필수):** MVP 판정 경로는 입력을 저장·로깅하지 않고 처리 후 폐기한다. 전송 TLS, CORS는 프론트 오리진으로 제한. 계측은 개인 식별 정보와 분리된 익명 이벤트만(PRD 9장). 후속 기능(H3 알림 등)의 저장은 *다른 데이터*이며 명시 고지 후 도입한다(PRD 9장 "저장 필요 시 고지").

### D3. 프론트 — Next.js (App Router) + TypeScript

분기 질문 입력·결과·근거·핸드오프 UI. 판정은 백엔드 `POST /verdicts` 호출로 수행. React 생태계·AI 학습 데이터가 풍부해 1인+에이전트 체제에 유리, vercel 배포 용이.

### D4. 규칙 엔진 — Java 직접 구현

노드 4종(all_of/any_of/not/atom) + 원자 11개 + Kleene 3치. rule DSL(JSON)을 파싱·평가하는 엔진을 외부 규칙엔진 없이 직접 구현한다. 규모가 작아 직접 구현이 투명하고 테스트가 쉽다.

### D5. 테스트 — 백엔드 JUnit 5 / 프론트 Vitest + Playwright

백엔드는 JUnit 5로 단위·골든셋 eval, 프론트는 Vitest(단위)·Playwright(수용 기준 E2E, F-001 등). 양측 green-before-merge 게이트.

### D6. 빌드·배포 — Gradle/Docker(백엔드), pnpm/Vercel(프론트)

- 백엔드: Gradle 빌드 → Docker 이미지 → JVM 호스트(Fly.io·Railway·Render·Cloud Run 중 5b에서 확정).
- 프론트: pnpm → Vercel.
- 두 배포·CORS·CI 두 파이프라인.

### D7. 계약 파이프라인 — contracts/가 언어중립 SSOT

`contracts/`의 openapi·JSON Schema에서 **Java 모델**(openapi-generator/jsonschema2pojo)과 **TS 타입**(openapi-typescript/json-schema-to-typescript)을 각각 생성한다. 두 언어가 한 계약에서 타입을 얻어 드리프트를 막는다.

## 기각된 대안

### D1
- **Next.js route handler 풀스택** — 단일 배포로 단순하나 route handler는 JS/TS라 Java 백엔드(D2)와 언어 불일치로 채택 불가.

### D2
- **TS 백엔드(NestJS/Fastify)** — 프론트와 타입 공유가 최상이고 이 서비스엔 기능상 충분하다. 다만 합계형 exhaustiveness(sealed/switch)와 Spring의 로드맵 1급 지원(배치·스케줄링·영속화)에서 Java/Spring이 앞서고, 유지보수자 역량(JS/TS 취약)과도 정렬돼 후자를 택함.
- **Go** — 경량·동시성 강점으로 가능하나, 도메인 합계형 표현·엔터프라이즈 로드맵 기능(배치·ORM) 성숙도에서 Spring 대비 조립 비용이 크다.
- **클라이언트 사이드 판정** — 입력 미전송으로 프라이버시 최강이나, 로드맵(서버·저장 요구)과 불일치하고 판정 코어를 TS로 두게 되어 유지보수자 역량과도 어긋난다. 미저장·무로깅 제약으로 서버 사이드의 프라이버시 격차를 좁힌다.

### D4
- **Drools 등 Java 규칙엔진** — 3치 Kleene·값 유형 사전분류를 직접 표현하기 어렵고 우회 비용·러닝이 크다. 규모가 작아 직접 구현이 투명·경량.

### D6
- **Maven** — 가능하나 Gradle의 간결함·Kotlin DSL 선호. 취향 차이라 뒤집어도 무방.
- **Vercel에 백엔드까지** — Vercel은 JVM 상시 서버에 부적합. 백엔드는 컨테이너 호스트로 분리.

## Consequences

- 저장소 구조: 루트에 `backend/`·`web/`·`contracts/`·`adr/`·`docs/` 등. `contracts/`가 두 언어의 SSOT가 되어 ADR-0001 계약 우선 철학이 실전 검증된다.
- **미저장·무로깅·처리 후 폐기·TLS·CORS 제한**이 백엔드 코드·배포의 강제 조건(위반 시 D2 근거 붕괴, 보안 리뷰 체크 항목).
- 두 배포·CORS·CI 두 파이프라인으로 복잡도가 오른다 — Java 백엔드를 별도 서비스로 두는 데 따르는 비용이다.
- Java/Spring은 소규모 stateless 서비스엔 상대적으로 무겁다(기동 시간·메모리·보일러플레이트). 도메인 안전성·로드맵 적합성·성숙도를 얻기 위해 감수하는 비용이다.
- 프론트(Next.js/TS)는 AI 에이전트 주도로 작성된다. 유지보수자가 JS/TS에 약해 프론트 코드의 검증·디버깅이 백엔드보다 어려울 수 있다 — 인지된 리스크이며, 계약(contracts/)과 E2E(Playwright, F-수용기준)로 동작 기준 검증해 완화한다.
- `contracts/openapi.yaml`의 `POST /verdicts`가 실제 계약이 된다 — 응답 형식(선발 고지·근거·링크 = 정책 레코드, DOMAIN 5장 후속)이 정해지면 freeze. 현재 초안 유지.
- accept 후: `ARCHITECTURE.md`를 이 스택으로 갱신, `CLAUDE.md`의 "기술 스택"·"자주 쓰는 명령어" TBD를 채운다(5b 스캐폴딩).

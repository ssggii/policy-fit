# ADR-0001: 문서 체계

- 상태: accepted
- 날짜: 2026-07-14

## Context

1인 개발 + AI 에이전트 루프 체제. 에이전트는 세션마다 기억이 리셋되므로,
결정의 근거가 문서에 없으면 기각된 선택지를 반복 제안한다.
문서가 많을수록 상호 링크 동기화 비용이 커지고, 같은 정보가 두 곳에 있으면 반드시 어긋난다.

## Decision

문서를 세 그룹으로 나눈다: 제품 문서(사람이 결정) / 계약 파일(기계가 검증) / 운영 문서(에이전트가 참조).
분할 기준은 갱신 트리거 — 트리거가 같으면 합치고, 다르면 나눈다.

- 기능정의서·범위표·요구사항 명세 → `SPEC.md` 하나로 통합 (트리거 동일: "만들 것이 바뀔 때")
- 판정 의미론 → `DOMAIN.md`로 분리 (트리거 상이: 정책 개정 시에만)
- 아키텍처의 '왜' → ADR, '현재 모습' → `ARCHITECTURE.md` (accept된 ADR로만 갱신)
- 문서 맵·라우팅 표 → `CLAUDE.md`에 직접 (에이전트 진입점에서 홉 제거)
- 계약은 산문 없이 스키마 파일만 (`contracts/`)

## 기각된 대안

- docs/README.md에 문서 맵 배치 → 에이전트 기준 CLAUDE.md에서 한 홉 추가. 라우팅 표는 15~20줄이라 CLAUDE.md 비대화 우려도 없음
- 기능정의서/범위표/명세 분리 유지 → 갱신 트리거가 같기 때문에 링크 동기화 비용만 발생. 다인 팀 관행이지 1인 체제 근거 없음.
- domain/ 디렉토리 선제 생성 → 파일 하나짜리 디렉토리는 라우팅만 복잡하게 함. 서브도메인 2개 시점에 분리 (CLAUDE.md 문서 규칙에 명시)
- 산문 계약서 + 스키마 병행 → 이중 기록은 반드시 어긋남

## Consequences

- SPEC.md가 커질 수 있음 — 비대해지는 시점에 분할 재검토
- ARCHITECTURE.md 갱신이 ADR accept에 묶여 있어 소소한 구조 변경도 ADR을 요구함 — 대상을 "되돌리기 비싼 결정"으로 한정해 완화

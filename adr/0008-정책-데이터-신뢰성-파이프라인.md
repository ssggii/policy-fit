# ADR-0008: 정책 데이터 신뢰성 파이프라인

- 상태: proposed
- 날짜: 2026-08-13
- 관련: `docs/policy-coverage-audit.md`, PRD 9장(데이터 정확도), ADR-0002 D4, ADR-0004 D6, ADR-0005, DOMAIN §4.4, 이슈 #73

## Context

판정에 쓰이는 값(기준액·연령·중위소득·신청 채널)이 어떻게 들어오고 어떻게 유지되는지에 대한 규약이 없다. 현재 상태:

- **출처가 자유 산문이다.** `policies/*.json`의 `meta.source`가 같은 파일 안에서 `"주택도시기금"` 다섯 글자와 URL·인용·재검증 시점을 담은 세 줄짜리 서술을 오간다. 무엇이 검증됐는지 기계가 알 수 없다.
- **값을 사람이 직접 찾아 채운다.** 에이전트의 웹 검색 결과를 사람이 1차 출처로 다시 확인해 값을 넣는 방식이 반복됐다(#15·#33).
- **갱신 트리거가 없다.** 기준 중위소득은 매년 고시되고 순자산 기준은 통계 갱신값이다. 2027년 고시가 나오는 순간 판정이 **조용히** 틀리기 시작하지만 이를 알릴 장치가 없다.
- **누락을 감지할 수 없다.** 값이 틀린 것은 다시 찾아보면 잡히지만, **원문에 있는데 rule에 안 넣은 요건**은 검색 대상에조차 오르지 않는다.

2026-08-13 감사(`docs/policy-coverage-audit.md`)에서 마지막 항목이 실증됐다 — MVP 3종 **전부**에서 rule에 없는 요건이 나왔고(주택드림 3·버팀목 6·청년월세 10), 방향은 대부분 FP다. Sprint 3에서 확정한 FP baseline 0/22는 **요건이 rule에 없어 골든셋에도 없는 상태**에서 측정된 값이라 현재 무효다.

같은 감사에서 외부 출처의 신뢰도 편차도 실측됐다:

| 관측 | 내용 |
|---|---|
| 공공 API에 판정 경계 금액이 없다 | 온통청년 청년정책 API의 `earnMinAmt`·`earnMaxAmt`가 모두 `"0"`, 실제 조건은 `earnEtcCn` 산문 |
| 공공 API가 틀린 값을 준다 | 청년월세에 `sprtSclLmtYn: "N"`(지원규모 제한 없음). 1차 출처는 "6만명 선정 예정, 초과 시 소득·재산 낮은 순 선정" |
| 아그리게이터·검색 결과가 틀린다 | "2026년부터 상시 신청 전환" 서술 다수. 1차 출처는 한시 접수(3.30~5.29). #33의 자산 3.37억 오류와 같은 경로 |
| 1차 출처가 기계 판독 불가일 수 있다 | 복지로(`WLF00004661`)는 SPA라 자동 수집 시 로딩 플레이스홀더만 반환. 사람이 브라우저로 확인해야 했다 |

**전제(이 전제가 깨지면 재검토 대상):**

- 판정 대상 정책이 **3~5종** 규모다(SPEC 1.1). 수십 종이 되면 D1·D7이 재검토 대상이다.
- 배포 대상이 미결이다(ADR-0004 D6). 상시 실행 인프라를 전제할 수 없다.
- 판정 경로에 런타임 LLM이 없다(ADR-0002 D4, loop.md 게이트 3).
- 사용자 노출 전이다. 아래 FP 항목들은 잠재 오판이며 실피해는 발생하지 않았다.

## 어떻게 신뢰가 확보되는가

아래 결정들이 각각 무엇을 막는지 먼저 밝힌다. **이 ADR은 값을 더 정확하게 만들지 않는다** — 정확도는 1차 출처를 읽는 데서 나온다. 이 ADR이 하는 일은 **틀렸을 때 드러나게 만드는 것**이다. 현재 가장 위험한 것은 값이 틀린 것이 아니라, 틀렸는지 아닌지 알 방법이 없다는 것이다.

정책 JSON에 `"max_krw": 345000000`이 있을 때 지금은 다음을 답할 수 없다:

| 질문 | 현재 | 결정 후 |
|---|---|---|
| 검증됐나 | 알 수 없음 | `tier` |
| 누가 언제 확인했나 | 알 수 없음 | `verified_by`·`verified_at` |
| 어느 문서 어느 문장인가 | 산문에 있기도, 없기도 | `url` + `quote` |
| 언제 다시 봐야 하나 | 알 수 없음 | `recheck_after` |
| 원문에 있는데 빠뜨린 요건은 | **알 수 없음** | `covered_requirements` |

신뢰는 **확인 가능성**에서 나온다. 네 시점에서 지킨다:

1. **값이 들어올 때** (D2·D5·D7) — `quote`(원문 문장)를 적지 못하면 값을 넣을 수 없다. 아그리게이터 요약본으로 값을 채우는 경로가 구조적으로 막힌다. 원문 문장을 옮기려면 원문을 봐야 하기 때문이다.
2. **값이 저장소에 있는 동안** (D6) — 미검증·만료 값이 프로덕션에 조용히 남지 못한다. 현재는 `"1차 출처 대조 미완"`이라고 적힌 값이 판정에 그대로 쓰이고 있어도 아무 일도 일어나지 않는다.
3. **세상이 바뀔 때** (D4) — 2027년 중위소득 고시일에 우리 값은 그날부터 틀린다. `recheck_after` 만료가 그날 이슈를 만든다.
4. **요건이 빠졌을 때** (D3) — 값의 정확도가 아니라 **완전성** 문제다. 2026-08-13 감사의 20건이 이 층이다.

**한계를 분명히 한다:**

- **요건 누락은 기계가 잡지 못한다.** `covered_requirements`를 쓰는 주체가 rule에서 빠뜨렸다면 매핑에서도 빠뜨린다. 이 필드의 방어력은 기계 검증이 아니라 **원문을 줄 단위로 훑도록 강제하는 절차**와, 그 결과가 diff로 남아 리뷰 대상이 된다는 데서 나온다. D5의 산문 필드 대조는 사람이 볼 목록을 만들어 주는 보조일 뿐이다.
- **`machine_readable: false` 출처는 3번이 작동하지 않는다.** 복지로가 그렇고, 하필 갭이 가장 많은 정책이다. 방어선이 `recheck_after` 하나뿐이므로 주기를 보수적으로 잡아야 한다.
- **content hash 오탐이 잦으면 3번은 사실상 죽는다.** 알림을 무시하게 되기 때문이다. 정규화가 D4의 실질 난이도다.

## Decision

### D1. 판정 데이터는 git JSON에 둔다 (DB 미도입)

`backend/src/main/resources/policies/*.json`을 유지한다. DB로 옮기지 않는다.

근거는 규모가 아니라 **성질**이다. 판정 데이터는 1차 출처로 사람이 검증하고 승인해야 하며 변경 이력이 감사 대상이다. git에서는 **변경 이력이 곧 감사 로그이고 PR 리뷰가 곧 승인 게이트**다. DB로 옮기면 이 두 장치를 잃고 대체물을 새로 만들어야 한다.

**DB 도입 트리거**(하나라도 충족 시 재검토): 판정 대상 정책 20종 초과 · 정책 이력 조회가 제품 기능이 됨 · 판정 데이터를 런타임에 변경해야 하는 요구 발생.

> 카탈로그(전국 정책 목록 탐색)는 성질이 다른 데이터다 — 외부 동기화·미검증·대량. 별도 저장 계층을 갖는다. 본 ADR 범위 밖이며 ADR-0009(제안 예정) 소관이다.

### D2. provenance를 DSL **밖 형제 필드**로 구조화한다

정책 레코드 최상위에 `provenance` 필드를 둔다. `rule` 트리 안이 아니다.

```jsonc
{
  "id": "cheongnyeon-wolse",
  "rule": { /* … meta.source·year 그대로 유지 … */ },
  "provenance": {
    "income_self": {
      "publisher": "국토교통부",
      "document": "청년월세 특별지원 사업안내",
      "url": "https://www.bokjiro.go.kr/…?wlfareInfoId=WLF00004661",
      "quote": "소득평가액이 … 기준 중위소득의 60% 이하",
      "tier": 1,
      "verified_at": "2026-08-13",
      "verified_by": "human",
      "recheck_after": "2027-08-01",
      "machine_readable": false,
      "content_hash": null
    }
  }
}
```

**DSL 밖에 두는 이유**: `contracts/rule-dsl.schema.json`의 `meta`는 `additionalProperties: false`에 `source`·`year`만 허용하는 frozen 계약이다. 여기를 확장하면 게이트 C(계약 변경)가 걸린다. ADR-0005가 `out_of_scope_gate`를 DSL 밖 형제로 둔 것과 같은 판단이며, DOMAIN §4.4("DSL은 자격 논리만 담당한다")와도 일치한다.

**관심사도 실제로 다르다:**

| | `meta.source`·`year` (DSL 내부, 계약) | `provenance` (형제, 내부) |
|---|---|---|
| 목적 | 사용자에게 보여줄 근거 문구 (F-004) | 검증 상태·재검증 관리 |
| 소비자 | web 결과 화면 | CI·감시 잡·사람 |
| 계약 | `openapi.yaml`에 노출됨 | 노출하지 않음 |

`tier`는 `docs/policy-coverage-audit.md` §1 등급을 따른다 — **1**=소관 부처·기금 원문 / **2**=공공기관 재게시 / **3**=아그리게이터·언론(사용 금지).

`machine_readable: false`는 복지로처럼 SPA라 자동 수집이 불가능한 출처를 표시한다. 이런 출처는 `content_hash` 감시 대상에서 제외되고 `recheck_after` 만료 알림에만 의존한다.

### D3. `covered_requirements` — 미커버 사유를 의무화한다

정책 레코드에 원문 요건 ↔ 원자 매핑을 기록하고, **rule이 덮지 않는 요건은 사유를 반드시 남긴다.**

```jsonc
"covered_requirements": [
  { "requirement": "청년가구 총재산가액 1.22억원 이하", "atom": "asset_self" },
  { "requirement": "임차보증금 3억원 이하", "atom": null, "uncovered_reason": "input_not_collected" },
  { "requirement": "시·군·구청장이 생계를 달리한다고 인정", "atom": null, "uncovered_reason": "admin_discretion" }
]
```

`uncovered_reason` 어휘: `out_of_mvp_scope` · `admin_discretion` · `input_not_collected` · `not_self_assessable`.

이 필드가 없어서 오늘 감사의 🔴 항목들이 **누락인지 의도적 제외인지 판별되지 않았다.** 앞으로 "덮지 않기로 했다"는 명시적 기록이 되고, 기록이 없으면 누락이다.

`input_not_collected`·`admin_discretion`으로 표시된 요건은 결과 화면에서 **판정 한계로 고지**되어야 한다(F-005 추정 고지·F-007). 조용히 통과시키지 않는다.

### D4. 변경 감지는 결정론으로만 한다

세 신호로 이슈를 자동 생성한다. **판단에 LLM을 쓰지 않는다.**

| 신호 | 조건 | 대상 |
|---|---|---|
| content hash 변경 | 저장된 `content_hash` ≠ 현재 | `machine_readable: true`인 출처 |
| 재검증 만료 | `recheck_after` ≤ 오늘 | 전체 |
| API 대조 불일치 | 온통청년 구조화 필드 ≠ 우리 값 | 대응 필드가 있는 항목 |

산출물은 **이슈 생성까지**다. 값을 자동으로 고치지 않는다.

### D5. 공공 API는 tier 2 — 값의 출처로 쓰지 않는다

온통청년 API는 **변경 신호와 커버리지 감사 입력**으로만 쓴다. 어떤 값도 API에서 직접 정책 레코드로 들어가지 않는다.

- **구조화 필드**(`sprtTrgtMinAge`·`sprtTrgtMaxAge`·`aplyUrlAddr`·`aplyYmd`): 우리 값과 자동 대조 → 불일치 시 이슈. **이슈는 "API가 옳다"가 아니라 "1차 출처를 다시 보라"는 뜻이다.**
- **산문 필드**(`etcMttrCn`·`addAplyQlfcCndCn`·`ptcpPrpTrgtCn`): 커버리지 감사 입력. 사람이 D3 매핑과 대조한다.

근거는 Context의 실측이다 — `sprtSclLmtYn: "N"`을 신뢰했다면 청년월세를 "지원규모 제한 없음"으로 인코딩했을 것이다.

### D6. CI 게이트는 2단계로 도입한다

| 단계 | 조건 | 동작 |
|---|---|---|
| 1 (본 ADR accept 직후) | `tier: 3` 또는 `recheck_after` 만료 또는 `provenance` 누락 | **경고 리포트**(빌드 통과) |
| 2 (요건 커버리지 해소 완료 후) | 위와 동일 | **빌드 실패** |

지금 하드 차단을 켜면 3종 전부 즉시 실패한다(주택드림은 `meta.source`가 `"국토교통부"` 다섯 글자다). 그건 게이트가 아니라 장애다. 1단계가 남은 부채를 가시화하고, 부채가 0이 된 시점에 2단계로 승격해 회귀를 막는다.

### D7. LLM은 제안까지, 확정은 사람이 한다

LLM은 1차 출처 원문을 읽고 **후보 값·후보 요건 매핑을 제시할 수 있다.** 확정은 사람이 한다.

- 제시에는 **`quote`(원문 문장)와 tier 1 `url`이 반드시 동반**된다. 문장을 제시하지 못하면 값이 들어갈 수 없다.
- LLM이 만든 항목은 `verified_by: "llm_proposed"` 상태다. **D6 게이트는 이를 검증된 값으로 인정하지 않는다.**
- 사람이 `quote`가 원문에 실제로 존재하는지 대조해 승인해야 `verified_by: "human"`으로 승격된다.
- 빌드타임 한정이다. 판정 경로(런타임)에는 여전히 LLM이 없다(ADR-0002 D4, 게이트 3).

**근거**: 2026-08-13 감사에서 발견된 20건은 LLM이 1차 출처를 가져와 우리 rule과 대조해 찾은 것이다. 사람이 원문을 정독해 찾은 것이 아니다(사람은 SPA라 수집 불가한 복지로 본문을 공급했다). 원문 읽기를 금지하면 실제로 작동한 경로를 막게 된다.

**환각·누락 위험은 D2가 이미 처리한다.** `quote` 강제로 없는 요건은 살아남지 못하고, tier 규율로 잘못된 출처가 걸러진다(같은 감사에서 검색 결과의 "2026년 상시 신청 전환" 서술이 tier 3이라 배제됐고, 실제로 오보였다). 사람의 검증 비용은 **원문 정독이 아니라 문장 한 줄 대조**로 떨어진다.

> 카탈로그 탐색에서의 RAG·임베딩 검색은 판정 경로가 아니므로 본 결정의 대상이 아니다. ADR-0009 소관.

### D8. 감시는 GitHub Actions 스케줄로 실행한다

배포 대상이 미결(ADR-0004 D6)이라 백엔드에 상시 실행 로직을 넣으면 아직 정하지 않은 것 위에 의존성을 쌓는다. Actions는 이미 CI로 쓰고 있고, D4의 산출물이 **이슈 생성**이라 GitHub에 붙는 것이 자연스럽다.

배포가 확정되고 감시가 제품 기능(예: 사용자에게 "기준 갱신됨" 표시)이 되면 재검토한다.

## 기각된 대안

- **런타임 RAG로 판정 근거를 조회** — 판정 경로에 LLM이 들어가 loop.md 게이트 3("판단 로직 런타임 LLM 누수 0")을 정면 위반한다. ADR-0002 D4가 자유 텍스트 LLM 파싱을 기각한 논리("파싱 오류 = 오판의 새 원천")가 그대로 적용된다. 검색 실패가 판정 실패가 되는 구조는 무인증 추정 판정의 신뢰도를 무너뜨린다.
- **공공데이터 API를 값의 출처로 삼아 자동 갱신** — 실측상 불가능하고 위험하다. 판정 경계 금액이 API에 없고(`earnMaxAmt: "0"`), 있는 필드마저 틀린다(`sprtSclLmtYn: "N"`). 지자체 레코드는 신선도 편차가 크다(창원시 레코드 `lastMdfcnDt` 2025-01-13). tier 2를 값으로 승격하는 순간 #33의 3.37억 오류가 자동화된다.
- **DB 도입** — D1 참조. 정책 3~5종에 배포·마이그레이션·백업 비용이 붙고, git이 이미 제공하는 감사 로그·승인 게이트를 잃는다. 배포 미결 상태에서 DB 의존성을 추가하는 것은 미결 위에 결정을 쌓는 것이다.
- **`meta`를 확장해 provenance를 DSL 안에 넣기** — `rule-dsl.schema.json`이 frozen이라 게이트 C가 걸리고, 사용자 노출용 근거(F-004)와 내부 검증 상태가 한 필드에 섞인다. ADR-0005가 같은 상황에서 형제 필드를 택한 선례가 있다.
- **`meta.source` 산문을 유지하고 작성 규율로 해결** — 지금까지의 방식이고, 그 결과가 같은 파일 안에서 다섯 글자와 세 줄이 공존하는 현 상태다. 기계가 읽을 수 없으면 CI도 감시도 붙지 않는다.
- **1차 출처 원문 전체를 저장소에 스냅샷** — hash 대신 전문을 커밋하면 diff로 변경 지점까지 보인다. 그러나 정부 사이트 HTML은 배너·세션·타임스탬프 노이즈가 크고, 복지로처럼 SPA면 애초에 수집이 안 된다. 저작권·용량 문제도 있다. `quote` 필드로 판정에 쓰인 문장만 남기는 것으로 충분하다.
- **LLM 사용 전면 금지 — 원문 읽기를 사람만 수행** (본 ADR 초안의 원안): 3~5종 규모에서 검증 부담이 절약분을 넘고 책임 소재가 흐려진다는 논리였으나, **읽기와 확정을 뭉뚱그린 결정이었다.** 2026-08-13 감사의 20건이 LLM의 원문 대조로 나왔다는 사실과 어긋난다. 규칙이 단순하다는 이점은 있으나(중간 상태 `llm_proposed` 불필요), 정책이 늘어나는 시점에 곧 병목이 되어 ADR을 다시 써야 한다.
- **LLM이 추출한 값을 사람 대조 없이 확정** — 틀렸을 때 책임 소재가 사라지고, 환각으로 없는 요건이 들어와도 걸러지지 않는다. D7은 제안까지만 허용하고 `quote` 대조를 통한 사람 승인을 확정 조건으로 둔다.

## Consequences

- **정책 레코드 형식이 바뀐다.** `provenance`·`covered_requirements` 두 필드가 최상위에 추가된다. `rule` 트리와 `contracts/rule-dsl.schema.json`은 **무변경**이다. 정책 레코드 전체 형식을 검증하는 스키마가 현재 없으므로 신설이 필요하다(`policy-record.schema.json`, contracts 소관 → 사람 승인).
- **3종 전부를 다시 써야 한다.** provenance 채우기는 1차 출처 재확인을 동반한다. 오늘 감사가 그 작업의 입력이므로 중복은 없다.
- **`openapi.yaml`은 이번에 변경하지 않는다.** provenance를 사용자에게 노출하지 않기 때문이다. "이 값은 언제 확인됐는가"를 신뢰 신호로 보여주자는 요구가 생기면 별도 계약 변경이다.
- **요건 커버리지 해소는 별도 등급 C 작업이다.** 세대주·독립거주·임차보증금·전용면적·중복대출·공공임대거주·소득신고이력 등 신규 원자는 `rule-dsl.schema.json`의 `atom` enum(frozen)과 DOMAIN §2.3 카탈로그를 함께 바꿔야 하고, 입력 질문 확장(F-001)과 `openapi.yaml` answers 변경까지 이어진다.
- **FP baseline 재측정이 뒤따른다.** 요건 추가 후 골든셋을 확충해 다시 재야 PRD 5장 수치가 의미를 갖는다.
- **content hash 정규화는 구현 시 해결한다.** 정부 사이트는 본문이 그대로여도 배너·세션ID·타임스탬프로 hash가 바뀐다. 본문 영역 추출·정규화 없이는 오탐이 반복된다. 이것이 D4의 실질 난이도이며, 오탐이 잦으면 `machine_readable: false`로 내려 `recheck_after`에만 의존하는 것이 대안이다.
- **`machine_readable: false` 출처는 자동 감지가 불가능하다.** 복지로가 그렇다. 이 경우 방어선은 `recheck_after` 만료 알림 하나뿐이므로, 주기를 보수적으로(정책 연간 공고 시점보다 앞서) 잡아야 한다.
- **감시가 Actions에 묶인다.** 배포 확정 후 감시를 제품 기능으로 올리려면 이전 비용이 발생한다. 지금은 미결 위에 쌓지 않는 편익이 더 크다고 판단했다.
- **`verified_by`에 상태 전이가 생긴다.** `llm_proposed` → (사람 `quote` 대조) → `human`. D6 게이트가 이 두 상태를 구분해야 하므로 조건이 하나 늘어난다. 정책 3종 단계에서는 거의 쓰이지 않을 수 있으나, 정책이 늘 때 ADR을 다시 쓰지 않아도 되는 값을 산다.

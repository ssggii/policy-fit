# 스프린트 운영 가이드 (AI 협업)

> 폴핏의 1인 개발 + AI 에이전트 체제에서 스프린트를 어떻게 굴리는지 정의한다.
> 작업 사이클 자체는 `loop.md`(1~7 게이트), 협업 규칙은 `CONTRIBUTING.md`가 소유한다. 이 문서는 그 위에 얹는 **스프린트 단위 운영**을 다룬다.

## 0. 전제

- **스프린트 단위**: 5 캘린더일(주말 포함, 연속). 예: Sprint 1 = 수~일, Sprint 2 = 월~금.
- **추정**: T-shirt(S=반나절 / M=1일 / L=2~3일). 스토리포인트는 쓰지 않는다(1인+AI라 과함).
- **트래커**: GitHub Projects(v2). 보드 필드 = Status(Todo/In Progress/In Review/Done) · Size · Sprint · Epic.
- **역할**: 사람은 **결정·승인·merge**만, AI가 나머지 실행(브랜치·구현·게이트·PR·집계·문서)을 담당한다.

## 1. 세리머니 매핑

원래 팀이 모여 하는 4대 세리머니를, 사람 회의 대신 AI·자동화로 대행한다.

| 세리머니 | 시점 | AI(에이전트) | 사람 |
|---|---|---|---|
| 계획 Planning | 스프린트 시작 | 백로그 조회 → 용량·의존성 고려해 후보 제안 → Sprint 필드에 담기 | 범위 승인 |
| 실행 + 데일리 | 매일 | 티켓 구현·게이트·PR, 매일 진행 요약 | 착수 지시·PR merge |
| 리뷰 Review | 스프린트 끝 | Done 티켓 → 릴리스 노트, 벨로시티 기록 | 확인 |
| 회고 Retro | 스프린트 끝 | `/retro` 실행 → 운영문서 개선 제안 | 승인 |

## 2. 계획 (Planning)

목표: 이번 5일에 할 것을 **용량 안에서** 확정한다(무한정 담지 않는다).

1. AI가 백로그(Todo·미배정)를 Epic·Size·의존성과 함께 조회한다.
2. AI가 스프린트 후보를 제안한다 — 대략 L1+M1+S2 기준, 의존성 반영(예: #8은 #10 선행).
3. 사람이 승인·조정한다.
4. AI가 승인된 이슈를 `Sprint N`으로 태깅한다(Sprint 필드).

산출물: Sprint N 백로그 확정(보드 `sprint:"Sprint N"`) + **목표 한 문장**(보드 Sprint 필드 옵션의 description).

**계획은 보드에서 끝낸다 — 문서 PR을 만들지 않는다.** 목표는 리뷰(§5)에서 달성 여부를 판정하는 기준이므로 계획 시점에 옵션 description으로 기록하고, `docs/sprint-review.md`에는 스프린트 종료 시 리뷰 로그와 함께 옮겨 적는다.

> 보드 Sprint 옵션을 추가할 때 쓰는 `updateProjectV2Field`는 **옵션 목록을 통째로 교체**한다. 기존 옵션 ID가 재발급되어 이미 배정된 아이템의 Sprint 값이 전부 지워지므로, 실행 전 현재 배정을 스냅샷으로 남기고 실행 후 복구한다(2026-08-13 Sprint 4 추가 시 18건 유실·복구).

## 3. 실행 (Execution)

스프린트의 몸통. **티켓 1개 = `loop.md` 작업 사이클 1회**이며, 보드 상태는 자동 전환된다(`project-automation.yml`).

한 티켓의 흐름:

```
1. 착수    사람 "#N 해" → AI가 브랜치 type/<N>-<F-ID>-슬러그 생성
              → [자동] Todo → In Progress
2. 구현    AI가 backend/web 서브에이전트로 구현 (loop.md 게이트 0·2)
3. 게이트  AI가 consistency-reviewer(3) + code-reviewer(3-1) 실행, 위반 시 수정·gate-log 기록
4. 완료체크 AI가 이슈 완료조건 체크박스 [x] (규율: 완료한 것만 체크)
5. PR      AI가 PR 생성 → [자동] In Progress → In Review
6. merge   사람이 CI green 확인 후 merge (게이트4) → [자동] In Review → Done, 이슈 close
7. 동기화  AI가 로컬 main 동기화 + 브랜치 정리
```

사람의 개입은 1(착수 지시)·6(merge)뿐. 이를 스프린트 항목 수만큼 반복한다.

## 4. 데일리 (Daily)

목표: 매일 "어디까지 왔나" 점검.

- **현재**: 사람이 요청하면 AI가 보드에서 요약한다 — 어제 Done / 오늘 In Progress / In Review 대기 / 막힌 것 / 남은 용량.
- **향후(#24)**: Hermes gateway가 매일 정해진 시간에 이 요약을 Slack으로 자동 push한다. 데일리 스탠드업의 대체.

## 5. 리뷰 (Review)

목표: 완성물 확정 + 속도 측정.

- AI가 Done 티켓을 모아 릴리스 노트를 생성한다(Closes로 연결된 PR·변경 요약).
- AI가 벨로시티를 기록한다. 2~3 스프린트 누적되면 "5일 용량"이 데이터로 잡혀 계획 정확도가 오른다.
- 미완 티켓은 다음 스프린트로 이월하거나 백로그로 반환한다. 자주 넘치면 다음 계획에서 덜 담는다.

## 6. 회고 (Retrospective)

목표: 다음 스프린트 개선점 도출. 회고는 2단이며(loop.md §9) **이 단계가 "승격 판정"** — 티켓마다 쌓인 관찰(gate-log·메모리)을 스프린트 범위로 집계해 임계(3회 누적·반복 차단)를 넘은 것만 승격한다.

- AI가 `/retro`를 실행한다 — 티켓별 관찰 + `docs/gate-log.md`를 **스프린트 전체로 집계**해, 임계를 넘은 것만 운영문서 개선(CLAUDE.md·CONTRIBUTING·loop.md 등)을 diff로 제안한다.
- 사람이 승인하면 개선점이 다음 스프린트 계획의 입력이 된다. 이 되먹임이 스프린트를 순환시키는 엔진이다.

## 7. 한눈에

```
Day 0   계획      AI 제안 → 사람 승인 → Sprint N 확정
Day 1~5 실행      [티켓마다] 착수(사람) → 구현·게이트·PR(AI) → merge(사람) → Done(자동)
         데일리    AI 요약 (→ 향후 Hermes/Slack 자동)
Day 5   리뷰      AI: 릴리스 노트 + 벨로시티
         회고      AI: /retro → 개선 제안 → 사람 승인
                  ↓ 개선점이 다음 계획으로
Day 0'  다음 계획  반복
```

사람의 개입 지점은 4곳: **계획 승인 · 착수 지시 · PR merge · 회고 승인.** 나머지는 AI가 채운다.

## 8. 보드 뷰 (참고)

Projects 뷰는 API로 생성 불가(UI 전용). 스프린트 확인용 권장 뷰:

- **스프린트별** (Table, Group by: Sprint) — 관리 0, 모든 스프린트가 그룹으로 보임.
- **현재 스프린트** (Board, Group by: Status, filter `sprint:"Sprint N"`) — 데일리 칸반. 새 스프린트 시작 시 필터를 수동 갱신.
- **백로그** (Table, Group by: Epic, filter `no:sprint`) — 전체 백로그 목록

뷰 없이도 AI가 요청 시 채팅으로 현황을 보고한다.
